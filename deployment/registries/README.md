# Deployment registries

Place one reviewed registry-source bootstrap JSON file here per target before enabling the offline
assembly workflow. The demo command generates examples with local URLs and
throwaway keys; do not use those keys for production.

The bootstrap pins the authority's TUF root and feed endpoint for online use,
and an independent archival authority key/policy for offline use. The registry
pins the configured publishers' public keys and component allowlists,
season/channel/target, repository base URLs, minimum accepted repository revisions,
and the bundle public key. Each publisher also has independent `tuf` trust; online catalogs authenticate `releases/<revision>/release.json` and its payload hashes. The bundle signing private key is the Actions
secret `BUNDLE_SIGNING_KEY` (PEM text); publisher keys remain in their own workflows.
The separate archival authority key signs records intended for offline bundles
and must not be supplied to ordinary publisher or assembly jobs. Online clients
authenticate those records through TUF and do not depend on the old archival pin.

See [CI signing and publication](../ci-signing.md) for publisher releases and
registry renewal through R2/S3 or Artifactory. The [offline download workflow](../offline-bundles.md)
now also publishes complete ZIPs, signed metadata, and browser pages, preserving
the prior selection until the new download is verified.

Set `BUNDLE_ASSEMBLY_ENABLED=true` after adding trusted bootstrap files,
`deployment/bundle-publications/*.json` destinations, and the bundle signing/storage
secrets. Initialize each destination explicitly through the manual workflow.
Publisher workflows may request `package-published` dispatches after their index
is visible; the schedule reconciles missed events. Online releases remain independent
of bundle publication. Publication requires the native Windows/macOS/Linux gates
and validation of each exact candidate on its matching host. Real payload-specific
acceptance remains as described in the proposal. TUF setup and archival policy are implemented in [the TUF guide](../tuf.md).

## Bootstrap and automatic refresh

The client receives this bootstrap through a trusted installation/configuration
channel. Example placeholders must be replaced with actual values:

```json
{
  "kind": "registry-source",
  "schema": 1,
  "registry_id": "wpilib-2027-stable-linux-x64",
  "target": "linux-x64",
  "season": "2027",
  "channel": "stable",
  "public_key": "BASE64_ENCODED_RAW_REGISTRY_AUTHORITY_KEY",
  "url": "https://packages.example.org/2027/stable/linux-x64/registry/registry.json",
  "minimum_revision": 1,
  "archive_policy": {"name": "wpilib-archive-v2", "lifetime": "indefinite"},
  "tuf": {"repository_id": "registry-2027-stable-linux-x64", "url": "https://packages.example.org/2027/stable/linux-x64/registry/tuf", "root": {}}
}
```

Replace the empty `root` placeholder with the complete signed object generated by `tools/tuf_admin.py`; it is not a URL. Never deploy the placeholder.

`run`, `check-updates`, `bundle`, and `publish` resolve this source before reading
publisher metadata. `refresh-registry` explicitly refreshes and reports the status,
identity, revision, digest, publishers, and profiles as JSON. No bootstrap or binary
edit is needed when the authority adds a publisher/profile in a signed revision.

The authority TUF catalog contains an archival Ed25519 envelope with `signed` and `signature` fields.
Its signed object contains `kind: registry`, schema `1`, `registry_id`, a positive
increasing `revision`, UTC epoch-second `issued_at` and online `expires_at`, explicit
`offline_expires_at: null` for indefinite authorization, and
the registry configuration described below. The authority signature covers all
of those values. Publication creates an immutable archival record and a hash-prefixed TUF catalog, then publishes targets/snapshot metadata and commits timestamp last. Local demo generation additionally writes `registry.json` for inspection. Renew online registry authorization by publishing a higher record revision; never change an existing record. Online TUF metadata renews independently every day.

The cache under `<cache>/registries/<tuf-authority-and-scope-hash>/current.json` retains
the last verified envelope and its exact TUF metadata/catalog evidence. It rechecks
the pinned root chain, role signatures, versions, and hashes on every read. A newer valid
revision atomically replaces it under an OS-owned refresh lock; process exit releases
the lock. Concurrent callers receive a retry error rather than racing to publish
an older cached view. Endpoint or archival-key changes retain the same TUF authority/scope cache.
Persist and reuse this cache across client runs; its signed revision is the online
rollback floor. Clearing it loses observed history, leaving the bootstrap's floor.

A transport failure may use the unexpired verified cache, reporting
`verified-cache` and a warning. An expired cache, invalid signature, wrong scope,
rollback, malformed feed, or same-revision content change fails instead. A failed
candidate does not overwrite the last good cache. An expired cached document still
provides a floor while fetching a new revision; it never authorizes an online
fallback without current-clock TUF verification. Older key-namespaced cache floors
are migrated after verification with the original archival key. Defaults are 7 days online and
indefinite offline authorization. `--valid-days` controls online lifetime; omit
`--offline-days` for v2. Bounded v1 deployments still use that legacy setting.
Protect the authority key and arrange periodic renewal before online expiry.

Example publication using demo files (the live bootstrap remains unchanged):

```sh
python -m installer_prototype publish-registry --registry build/demo/registry.json --source build/demo/registry-source.json --key build/demo/keys/registry.pem --revision 2 --output build/demo/store/linux-x64/registry
```

The assembly workflow resolves the bootstrap and pins the returned signed document.
It does not require the registry authority's private key. It needs the bundle key
that the selected registry authorizes. TUF roots rotate through their verified chain,
including histories beyond 256 rotations. An incomplete bounded catch-up reports
`root-update-pending` and resumes when retried with the same cache. Rotating the
archival authority key does not interrupt online clients; new offline media still
requires a matching explicitly trusted bootstrap. Emergency recovery and hardened
local-state protection remain separate operational work.

## Registry contract

The registry is trusted configuration. Publishers cannot authorize themselves or
change another publisher's component ownership through repository metadata.
Any nonempty set of publishers is supported; none of the original project names
is required. The existing schema version remains `1`.

| Field | Meaning |
| --- | --- |
| `schema`, `season`, `channel`, `target` | Schema `1` and the release/platform selection, checked against signed repository metadata. |
| `repositories` | Map of publisher IDs to URL, public key, component allowlist, and optional revision floor. Every configured repository is required for a complete view. |
| `repositories.<id>.url` | HTTPS repository base URL; local file and loopback HTTP URLs are supported for development. |
| `repositories.<id>.public_key` | Base64-encoded raw 32-byte Ed25519 archival release key. |
| `repositories.<id>.tuf` | Independent repository ID, TUF base URL, and complete signed bootstrap root. |
| `online_trust` | `tuf` for production; requires TUF configuration for every publisher. |
| `archive_policy` | Must match the source bootstrap: `wpilib-archive-v2` with `lifetime: indefinite`; bounded v1 remains supported explicitly for earlier media. |
| `repositories.<id>.components` | Nonempty list of exact component IDs owned exclusively by this publisher. Duplicate ownership is rejected before fetching metadata. |
| `repositories.<id>.minimum_revision` | Positive minimum accepted signed revision; defaults to `1`. |
| `repository_order` | Optional list of every configured publisher exactly once, in compatibility-selection precedence order. If omitted, publisher IDs are sorted alphabetically; JSON object ordering never affects precedence. |
| `profiles` | Optional map of profile names to component-ID lists. These IDs must have configured owners and must be present in the selected snapshots when the profile is installed. |
| `bundle_public_key` | Trusted Ed25519 key authorizing offline bundle manifests. Required for bundle operations. |

Publisher IDs are lowercase slugs of up to 64 characters, beginning with a letter
and containing only letters, digits, `_`, or `-`. Reserved Windows device names
are rejected because IDs also become local directory names. Component IDs retain
the prototype's lowercase dotted-ID syntax.

To add RobotPy to an existing registry, add an entry shaped like this, substituting
the actual key and target-specific URL:

```json
{
  "robotpy": {
    "url": "https://packages.example.org/2027/stable/linux-x64/robotpy",
    "public_key": "BASE64_ENCODED_RAW_ED25519_PUBLIC_KEY",
    "components": ["org.robotpy.python", "org.robotpy.sdk", "org.robotpy.deploy"],
    "minimum_revision": 1,
    "tuf": {"repository_id": "robotpy-2027-stable-linux-x64", "url": "https://packages.example.org/2027/stable/linux-x64/robotpy/tuf", "root": {}}
  }
}
```

Replace `root: {}` with RobotPy's reviewed signed root object. Also extend `repository_order` if present, and add a profile such as
`"python": ["org.robotpy.sdk", "org.robotpy.deploy"]`. Package dependency metadata
brings in the Python runtime. Use the normal `publish` command with a matching
specification and publisher key. Real Python/wheel packaging remains separate
work; the demo's packages are markers.

Repository selection examines up to eight revisions per publisher, tries descending
revisions in the configured precedence order, and fails explicitly after 4,096
combinations. All configured repositories remain required if any is unavailable
or fails verification. This limit makes adding publishers predictable without
silently returning a partially checked combination.

## Offline registry snapshots and compatibility

New TUF bundles use manifest schema `3` and the explicit [archival policy](../tuf.md#explicit-offline-policy-wpilib-archive-v2). They contain `registry.json`, the exact signed
registry envelope used during assembly; the signed bundle manifest binds its
identity, revision, and SHA-256. Download metadata and bundle identity include that
binding too. A trusted bootstrap verifies the registry authority signature and its
explicit indefinite offline policy, then verifies the bundle with the key authorized by that
registry. A key merely supplied by the bundle cannot establish trust.

Offline mode does not fetch the registry feed or substitute the newest cached
registry. Its status is `verified-bundle`. A bundle built at revision 1 remains
usable after the client learns revision 2 adding RobotPy: completeness is checked
against the revision-1 publisher set. Offline use never overwrites the online cache
or lowers its revision floor. V2 media never expires; preserve its matching trusted
installer/bootstrap. A deliberately replaced bootstrap with a raised minimum
revision can still reject earlier media. Bounded v1 bundles retain their original
expiry and require a one-time rebuild to adopt v2. Offline clients cannot learn
current revocations.

Missing and unexpected publishers relative to the pinned registry are rejected.
A target with unsupported RobotPy payloads should omit that publisher and its
Python profiles from its authoritative registry rather than silently omitting it
during assembly.

Manually trusted local registries remain accepted for development. New bundles
created from those files carry a hash-pinned local snapshot but no authority-issued
revision; the external local registry must still match. Legacy schema-1 bundles
remain readable with their original matching local registry. Automatic source
mode requires a bundle with an authority-signed registry snapshot, and does not
silently downgrade to local/unverified trust for legacy media.
