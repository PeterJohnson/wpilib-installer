# Self-contained installer runtime

The delivered manager must start, install offline, and maintain an installation without asking the user to install Python, .NET, Java, Qt, a compiler, a VC redistributable, FUSE, or additional GUI libraries. This applies to the installer and its private engine. Packages such as RobotPy must separately declare/bundle their own application runtime. The OS, its base ABI, and a desktop display server remain prerequisites.

The selected distribution remains **one executable on Windows/Linux and one `.app` on macOS**, with GUI and JSON CLI modes in the same application. A ZIP is only a browser/download wrapper, not a separate runtime. The installed maintenance application retains the same embedded runtime after the original download and USB bundle are deleted.

## Linux implementation and AppImage decision

`tools/build_rust_manager.py` invokes the Ubuntu 22.04 Docker builder. Python, Docker, Cargo and IFW are **build/test tools only**. The Rust toolchain version and Cargo graph are pinned; Ubuntu package updates are resolved when the builder image is rebuilt, and their exact versions are recorded. This is not yet a bit-for-bit reproducible build.

`tools/package_rust_runtime.py` resolves the private Qt engine's ELF dependencies and explicitly seeds libraries loaded at runtime by the GUI. It recursively gathers dependencies and includes Mesa's `swrast_dri.so`/llvmpipe. `runtime.zip` is compiled into the manager alongside the private engine and public trust bootstrap. It contains a per-file SHA-256 manifest, package/source versions, fonts, XKB/locale data, and distribution copyright notices. The build emits `runtime.json` and `dependency-audit.json` alongside the application. Production distribution must also provide corresponding sources/relinking materials as required by the bundled libraries' licenses; retaining notices alone does not discharge those obligations.

At launch, the manager creates a private temporary directory, extracts its own compiled runtime, and starts the same executable with private library/data paths. The parent retains the directory until the child and Qt worker exit, then removes it. Mesa software rendering avoids a dependency on an installed GPU driver. No shell, archive utility, package manager, root access, mount, or FUSE service is needed on the client. A writable temporary location with executable mappings and sufficient space is required; `TMPDIR` can select one. Runtime extraction increases startup time and disk use. The internal re-execution marker is process bookkeeping, not a security boundary against an attacker controlling the launch environment or installation directory.

The initial launcher still needs the base GNU/Linux ABI (`glibc`, loader and `libgcc_s`); it does not support musl-only distributions such as stock Alpine. The runtime pins desktop libraries rather than depending on distro packages, so security updates to those libraries require rebuilding and redistributing the manager. Manager self-update/signing remains separate work.

An AppImage could carry the same libraries, but does not discover/bundle them automatically or eliminate the oldest-glibc build requirement. The [modern type-2 runtime](https://github.com/AppImage/type2-runtime) bundles libfuse, while normal execution still needs kernel/device FUSE access. Its [extract-and-run fallback](https://docs.appimage.org/user-guide/troubleshooting/fuse.html) needs an explicit argument/environment setting. The existing embedded-archive mechanism provides automatic extraction without that additional user requirement. An AppImage wrapper may be added later for ecosystem integration, but is not needed to meet the one-executable requirement. See also [AppImage deployment guidance](https://docs.appimage.org/reference/best-practices.html).

## Acceptance and limits

`.github/workflows/rust-contained.yml` builds all four native targets, enforces dependency audits, and runs authenticated online/offline lifecycle tests. Linux also runs `tools/check_rust_clean_linux.py`: client containers have unmodified OS package sets, no network, read-only system files, no FUSE device, an empty tool PATH and an unprivileged UID. Xvfb and Weston are in separate display-server containers. No Python or build/test tools are installed in a client container. A negative control requires the unbundled Qt engine to fail for a missing shared library; loader traces require non-base libraries to come from the extracted runtime.

The clean tests render startup windows on X11 and Wayland, install and upgrade from offline bundles, delete the original executable and media, then remove/reinstall using the installed application and retained cache. Host-side checks verify payload hashes and inventory. Reports record image digests, base package inventory, application hash, loaded libraries and timings. Existing native online checks cover the same packaged executable's authenticated registry refresh, long root histories, verified caches and offline-to-online upgrade.

Windows/macOS native runners contain development tools; removing PATH and checking imports gives useful coverage but does not substitute for pristine desktop VM acceptance. The Linux containers share the host kernel and use test display servers; they do not establish every desktop/compositor or kernel version as supported. Download quarantine, Windows application signing/SmartScreen, macOS signing/notarization, accessibility and launcher integration remain release acceptance work. GUI software rendering is a portability choice; performance measurements should guide later changes.

## Validation — November 27, 2026

The [four-target run](https://github.com/PeterJohnson/wpilib-installer/actions/runs/46060475266) passed Linux and both Mac jobs at `12ca529`. Windows compiled successfully but the new audit initially omitted the OS-supplied [`combase.dll`](https://learn.microsoft.com/en-us/windows/win32/api/roapi/nf-roapi-roregisteractivationfactories); `22d8fca` corrected that allowlist and added a platform selector for targeted CI retries. The [Windows rerun](https://github.com/PeterJohnson/wpilib-installer/actions/runs/46061793559) passed. The fix does not change any shipped runtime code. [Saved evidence](evidence/self-contained-2026-11-27.json) records the exact runs, hashes, import audits, Linux image digests and check names.

Each native target passed 35 authenticated registry/cache/offline-to-online lifecycle checks and 11 unit tests. Linux additionally passed 10 checks in each of four unmodified OS images: **180 acceptance checks and 44 unit checks total**. The Linux images ran both X11 and Wayland, with first startup tests completing in 0.82–0.91 seconds including extraction, rendered screenshots and process exit on CI. Local repeats also passed all 40 clean-environment checks. These are fixture tests; the earlier real Elastic/AdvantageScope results are recorded separately in the Rust prototype document.

The tested Linux executable is **109,758,032 bytes (104.7 MiB)**; its browser ZIP is 96,580,592 bytes (92.1 MiB). The embedded runtime adds 80 shared libraries plus the software rendering driver and data, expanding to approximately 200 MiB. The downloaded application hash matched the tested binary and its ZIP retained executable permissions. This size/extraction cost buys independence from separately installed desktop libraries and FUSE. Windows/macOS retain their OS-native graphics libraries and do not carry this Linux runtime.
