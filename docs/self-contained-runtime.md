# Self-contained installer runtime

The delivered manager must start, install offline, and maintain an installation on a supported desktop OS without asking users to install Python, .NET, Java, Qt, a compiler, a VC redistributable, FUSE, or installer-specific libraries. Linux uses the desktop's graphics drivers. Its headless CLI requires only the base GNU/Linux ABI. Packages such as RobotPy separately declare/bundle their own application runtime.

Distribution remains **one executable on Windows/Linux and one `.app` on macOS**, with GUI and JSON CLI modes in the same application. A ZIP is a browser/download wrapper. The installed maintenance application retains the embedded Qt worker and its dependencies after the original download and USB bundle are deleted.

| Platform | Runtime policy | Validation |
| --- | --- | --- |
| Windows x64 | Static MSVC CRT; the private Qt engine imports Windows 10/11 inbox libraries only. | Regular/delay PE import audit; native GUI, offline-to-online updates and verified-cache maintenance with external tools removed from PATH. |
| macOS x64 / ARM64 | Embedded Qt worker; system frameworks/libraries only; deployment target macOS 13. | Audit both Mach-O binaries and minimum OS declarations; native lifecycle on macOS 15 for both architectures. Actual macOS 13 testing remains a release acceptance item. |
| Linux x64 GUI | glibc 2.35 baseline; a supported desktop supplies OpenGL/EGL, vendor drivers and X11/Wayland client libraries. Ubuntu Desktop 24.04 and 26.04 are the initial desktop acceptance targets. | Fresh installations from pinned official Desktop ISOs; native Wayland and X11 through XWayland; no extra guest packages. |
| Linux x64 CLI / private Qt worker | Base GNU/Linux ABI only; Qt's non-base dependency closure and fonts are embedded. No display, OpenGL, Mesa, LLVM, FUSE or installed Qt required. | Offline CLI lifecycle in unmodified Ubuntu 22.04/24.04/26.04 and Debian 12 images with no network, display or graphics packages. |

## Linux host graphics and private Qt libraries

`tools/build_rust_manager.py` compiles/links on Ubuntu 22.04 in Docker. Python, Docker, Cargo and IFW are **build/test tools only**. Rust/Cargo versions are pinned; Ubuntu package versions are recorded at build time. This is not a bit-for-bit reproducible build.

The manager uses the host desktop's graphics implementation. It does not force Mesa, software rendering, a GL vendor, an EGL ICD or a private library search path. Host graphics may use hardware acceleration or the OS-provided software renderer. A working graphical session and compatible OpenGL implementation are GUI prerequisites; base container/server images without a graphics stack are not desktop acceptance targets. Ubuntu's [26.04.1 Desktop manifest](https://releases.ubuntu.com/26.04/ubuntu-26.04.1-desktop-amd64.manifest) includes the GL/EGL, Mesa and Wayland/X11 packages needed for this baseline. Some Qt-specific XCB helpers are absent, so those remain bundled.

`tools/package_rust_runtime.py` gathers only the headless Qt worker's dependency closure and font data. The archive is compiled into the manager along with the worker and public trust bootstrap. It excludes Mesa/LLVM/ICU and graphics drivers, and the packager rejects their accidental reintroduction. A file/hash manifest, build package/source versions and distribution copyright notices accompany the runtime. Production distribution must also satisfy corresponding-source/relinking obligations; notices alone are not sufficient.

Immediately before launching Qt, `WorkerRuntime::prepare` creates a private temporary directory, extracts the compiled worker runtime and sets library/font paths **on that child command only**. Its guard stays alive through child exit and then removes the directory. The manager never re-executes under the Qt environment. In particular, host Mesa/vendor drivers cannot accidentally load the worker's older `libstdc++`, X11 or compression libraries. Verification, discovery and GUI startup do not extract the worker runtime. Installed maintenance uses the same path.

Stock Ubuntu 26.04 omits the X11 keyboard bridge used by winit, although its Wayland path works without it. `GuiRuntime::prepare` prefers the host `libxkbcommon-x11.so.0`; when unavailable in an X11 session (with no Wayland display), it extracts only `libxcb-xkb.so.1`, `libxkbcommon.so.0` and `libxkbcommon-x11.so.0` into a separate private directory. The XKB core and bridge must come from the same build because the bridge uses internal core structures. It loads this matched helper set by absolute path and retains their handles through GUI exit. Their base XCB dependency, OpenGL/EGL, vendor drivers, C++ runtime and all other GUI libraries still come from the OS. This reuses three small files already embedded for the worker, introduces no library-search environment changes and never exposes the Qt runtime directory to the GUI. Native Wayland acceptance removes `DISPLAY` and does not load this fallback. The fallback is built on the Ubuntu 22.04 baseline; newer optional compose keysyms can produce warnings and need separate international-input acceptance. Native Wayland and systems supplying the X11 bridge use their current OS XKB stack.

The launcher still needs glibc, its loader and `libgcc_s`; musl-only distributions such as stock Alpine are outside the baseline. Qt operations and the optional X11 compatibility fallback need a writable temporary location with executable mappings; `TMPDIR` can select one. Rebuilding the manager updates its private libraries, while the OS maintains graphics drivers. This retains the ordinary desktop “download and run” requirement, with a smaller supported surface than requiring graphical startup on a bare OS container. Manager self-update/signing remains separate work.

An AppImage is optional ecosystem packaging. It would not remove the host graphics contract or dependency audits. The current executable needs no mount or FUSE service. See [AppImage deployment guidance](https://docs.appimage.org/reference/best-practices.html) and its [FUSE fallback](https://docs.appimage.org/user-guide/troubleshooting/fuse.html).

## Acceptance and limits

`.github/workflows/rust-contained.yml` builds native targets, enforces dependency audits, and runs authenticated online/offline lifecycle tests. Linux also runs `tools/check_rust_clean_linux.py`: unmodified client OS package sets, no network/display/graphics/FUSE, read-only system files, an empty client PATH and an unprivileged UID. No test tools are installed in client containers. An unbundled Qt negative control fails for a missing dependency. Loader traces require every non-base worker dependency to come from the private runtime, reject GL/LLVM loading and confirm metadata-only commands need no worker runtime.

Dependent QEMU/KVM jobs use `tools/check_rust_desktop_vm.py` to install the stock `ubuntu-desktop` source from pinned, hash-verified Ubuntu 24.04.4 and 26.04.1 ISOs onto new disks. They boot the installed OS, not a container or a live session. The guest has no network interface during either installation or acceptance. No guest packages are installed for testing; the harness uses preinstalled Python's standard library, and removes external tools from the client's PATH. Test-only autologin and an autostart entry launch the suite. A dedicated shared directory transfers the application, browser ZIPs and evidence.

The Desktop suite is also independently dispatchable through `.github/workflows/rust-desktop.yml`: supply the source native workflow run ID as `application_run` and select `all`, `24.04.4` or `26.04.1`. It downloads that run's `ubuntu-desktop-test-input` artifact and records the tested executable hash, so harness fixes can be validated against the same application without rebuilding it.

Each desktop exercises native Wayland and X11 through the stock XWayland server: rendered startup, offline installation and upgrade, installed-manager startup, discovery and cached remove/reinstall after deleting original downloads/media. Payload bytes, modes and inventory are checked. Per-process loader traces require graphics and other GUI libraries to come from OS paths, allow only the three named X11 keyboard helpers from the compatibility directory, and require Qt libraries to come from the private worker directory. Reports preserve ISO/application hashes, guest OS/package inventory, timings, screenshots and library origins. Virtual graphics exercise the OS rendering stack; physical Intel/AMD/NVIDIA hardware remains separate coverage.

Windows/macOS hosted runners contain development tools; PATH isolation and import audits do not replace pristine desktop VM acceptance. macOS 13, download quarantine, Windows signing/SmartScreen, macOS notarization, accessibility and launcher integration remain release acceptance work. The previous all-bundled-renderer experiment and its measurements are historical evidence below, not the current Linux distribution contract.

## Current validation: host graphics

The [complete six-job CI run](https://github.com/PeterJohnson/wpilib-installer/actions/runs/46073080624) passed at `3789371`. [Saved evidence](evidence/host-graphics-2026-11-27.json) records the exact application and ISO hashes, native dependency audits, headless image digests, Desktop boot provenance, package inventories and screenshot hashes, and per-process loaded libraries.

All four native targets passed 35 authenticated online/cache/offline-to-online acceptance checks and 11 Rust unit tests each. Four minimal Linux containers passed nine headless checks each. Fresh Ubuntu 24.04.4 and 26.04.1 Desktop installations each passed 18 checks across native Wayland and X11 through XWayland, with no network interface and no added guest packages. That is **212 acceptance checks and 44 unit checks**. These use signed fixture packages; earlier real Elastic/AdvantageScope tests are documented separately in the Rust prototype document.

The Desktop runs verified that the GUI loads the OS graphics stack, the missing X11 keyboard bridge on Ubuntu 26.04 uses only the three allowlisted compatibility libraries, and Qt operations load their non-base dependencies from the worker's separate private directory. Both backends completed startup, offline installation and upgrade, and maintenance after deleting the original application and bundle media. Screenshots were also visually inspected.

## Historical validation: bundled-renderer build

The [four-target run](https://github.com/PeterJohnson/wpilib-installer/actions/runs/46060475266) passed Linux and both Mac jobs at `12ca529`. Windows compiled successfully but the new audit initially omitted the OS-supplied [`combase.dll`](https://learn.microsoft.com/en-us/windows/win32/api/roapi/nf-roapi-roregisteractivationfactories); `22d8fca` corrected that allowlist and added a platform selector for targeted CI retries. The [Windows rerun](https://github.com/PeterJohnson/wpilib-installer/actions/runs/46061793559) passed. The fix does not change any shipped runtime code. [Saved evidence](evidence/self-contained-2026-11-27.json) records the exact runs, hashes, import audits, Linux image digests and check names.

Each native target passed 35 authenticated registry/cache/offline-to-online lifecycle checks and 11 unit tests. Linux additionally passed 10 checks in each of four unmodified OS images: **180 acceptance checks and 44 unit checks total**. The Linux images ran both X11 and Wayland, with first startup tests completing in 0.82–0.91 seconds including extraction, rendered screenshots and process exit on CI. Local repeats also passed all 40 clean-environment checks. These are fixture tests; the earlier real Elastic/AdvantageScope results are recorded separately in the Rust prototype document.

The tested Linux executable is **109,758,032 bytes (104.7 MiB)**; its browser ZIP is 96,580,592 bytes (92.1 MiB). The embedded runtime adds 80 shared libraries plus the software rendering driver and data, expanding to approximately 200 MiB. The downloaded application hash matched the tested binary and its ZIP retained executable permissions. This size/extraction cost buys independence from separately installed desktop libraries and FUSE. Windows/macOS retain their OS-native graphics libraries and do not carry this Linux runtime.
