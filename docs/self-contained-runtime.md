# Self-contained installer runtime

The delivered manager must start, install offline, and maintain an installation on a supported desktop OS without asking users to install Python, .NET, Java, Qt, a compiler, a VC redistributable, FUSE, or installer-specific libraries. Linux uses the desktop's graphics drivers. Its headless CLI requires only the base GNU/Linux ABI. Packages such as RobotPy separately declare/bundle their own application runtime.

Distribution remains **one executable on Windows/Linux and one `.app` on macOS**, with GUI and JSON CLI modes in the same application. A ZIP is a browser/download wrapper. The installed maintenance application retains the embedded Qt worker and its dependencies after the original download and USB bundle are deleted.

| Platform | Runtime policy | Validation |
| --- | --- | --- |
| Windows x64 | Static MSVC CRT; the private Qt engine imports Windows 10/11 inbox libraries only. | Regular/delay PE import audit; native GUI, offline-to-online updates and verified-cache maintenance with external tools removed from PATH. |
| macOS x64 / ARM64 | Embedded Qt worker; system frameworks/libraries only; deployment target macOS 14. | Audit both Mach-O binaries and minimum OS declarations; native lifecycle on macOS 15 for both architectures. Actual macOS 14 testing remains a release acceptance item. |
| Linux x64 GUI | glibc 2.35 baseline; a supported desktop supplies OpenGL/EGL, vendor drivers and X11/Wayland client libraries. Ubuntu Desktop 24.04 and 26.04 are the initial desktop acceptance targets. | Fresh installations from pinned official Desktop ISOs; native Wayland and X11 through XWayland; no extra guest packages. |
| Linux x64 CLI / private Qt worker | Base GNU/Linux ABI only; Qt's non-base dependency closure and fonts are embedded. No display, OpenGL, Mesa, LLVM, FUSE or installed Qt required. | Offline CLI lifecycle in unmodified Ubuntu 22.04/24.04/26.04 and Debian 12 images with no network, display or graphics packages. |

## C#/Avalonia runtime boundary

The application lives in `client/`; see the [client guide](client.md) for operations and acceptance workflows. Builds emit `assets/sizes.json` with executable/download sizes and hashes.

`tools/build_client.py` compiles both NativeAOT executables on Ubuntu 22.04 in Docker, using SDK 11.0.100 and runtime 11.0.0. Windows/macOS publish natively. Python, .NET SDK, Docker and IFW are build/test tools only. The public launcher contains a compressed native GUI/CLI application plus Skia/HarfBuzz/Avalonia platform libraries, the bootstrap and Qt assets. It extracts into a fresh private directory rather than trusting a writable executable cache. No FUSE is needed.

The macOS deployment target follows the .NET 11 NativeAOT toolchain's default target of 14.0, set explicitly for both publishes and in the app bundle metadata. This is a compatibility target, not a tested support claim for macOS 14. Microsoft's [supported macOS versions for .NET 11](https://github.com/dotnet/core/blob/main/release-notes/11.0/supported-os.md) start at macOS 15; our native CI uses macOS 15. Intel macOS publishes explicitly disable the classic Xcode linker: Xcode 16's classic linker rejects an unaligned GSS symbol in the .NET 11 x64 native runtime archive. The current Apple linker remains subject to the same dependency audit and native lifecycle gates.

The Linux client has a private OpenSSL 3 pair for hashing/TLS, with its distribution notice. Its library search path contains only its own native application directory, plus a separate three-library X11 keyboard fallback when the host bridge is absent. That fallback contains matched `libxcb-xkb.so.1`, `libxkbcommon.so.0`, and `libxkbcommon-x11.so.0`. The GUI never inherits the private Qt library directory. Graphics drivers, GL/EGL, X11/Wayland and general desktop libraries remain host-provided; no Mesa/LLVM renderer is shipped. Native Wayland is selected explicitly because [Avalonia's platform detection defaults to X11/XWayland](https://docs.avaloniaui.net/docs/platform-specific-guides/linux). The Wayland backend remains experimental upstream and needs further production UX/accessibility evaluation.

Immediately before invoking Qt, `Installation.Qt` extracts the worker runtime and sets library/font paths on that process only. Verification and CLI discovery do not extract or load Qt dependencies. Retained maintenance uses the same path after original downloads are deleted. Worker/runtime packaging still comes from the minimal Ubuntu 22.04 image, with its hash/file and license manifests. Temporary storage must allow executable mappings; `TMPDIR` can choose it. Manager updates are needed to refresh private dependencies.

This is not a bit-for-bit reproducible build. Production signing/notarization, SBOM, source/relinking obligations and authenticated manager self-update remain required release work. An AppImage is optional wrapping; it would not remove the desktop graphics contract.

## Acceptance and limits

`.github/workflows/client.yml` builds native targets, enforces dependency audits, and runs authenticated online/offline lifecycle tests. Linux also runs `tools/check_headless_linux.py`: unmodified client OS package sets, no network/display/graphics/FUSE, read-only system files, an empty client PATH and an unprivileged UID. No test tools are installed in client containers. An unbundled Qt negative control fails for a missing dependency. Loader traces require every non-base worker dependency to come from the private runtime, reject GL/LLVM loading and confirm metadata-only commands need no worker runtime.

Dependent QEMU/KVM jobs use `tools/check_desktop_vm.py` to install the stock `ubuntu-desktop` source from pinned, hash-verified Ubuntu 24.04.4 and 26.04.1 ISOs onto new disks. They boot the installed OS, not a container or a live session. The guest has no network interface during either installation or acceptance. No guest packages are installed for testing; the harness uses preinstalled Python's standard library, and removes external tools from the client's PATH. Test-only autologin and an autostart entry launch the suite. A dedicated shared directory transfers the application, browser ZIPs and evidence.

The Desktop suite is also independently dispatchable through `.github/workflows/desktop-acceptance.yml`: supply the source native workflow run ID as `application_run` and select `all`, `24.04.4` or `26.04.1`. It downloads that run's `ubuntu-desktop-test-input` artifact and records the tested executable hash, so harness fixes can be validated against the same application without rebuilding it.

Each desktop exercises native Wayland and X11 through the stock XWayland server: rendered startup, offline installation and upgrade, installed-manager startup, discovery and cached remove/reinstall after deleting original downloads/media. Payload bytes, modes and inventory are checked. Per-process loader traces require graphics and other GUI libraries to come from OS paths, allow only named NativeAOT/Skia/HarfBuzz/OpenSSL libraries and the three X11 keyboard helpers from the private application directory, and require Qt libraries to come from the private worker directory. Reports preserve ISO/application hashes, guest OS/package inventory, timings, screenshots and library origins. Virtual graphics exercise the OS rendering stack; physical Intel/AMD/NVIDIA hardware remains separate coverage.

Windows/macOS hosted runners contain development tools; PATH isolation and import audits do not replace pristine desktop VM acceptance. macOS 14, download quarantine, Windows signing/SmartScreen, macOS notarization, accessibility and launcher integration remain release acceptance work.
